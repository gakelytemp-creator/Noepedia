# IDEAL_TO_REAL — იდეალური სამყაროდან გარეთ

**Status: CURRENT + WORKING HYPOTHESIS**  
**Date: 2026-10-15**

## 0. მთავარი შემობრუნება

Noepedia-ში ცოდნის მოძრაობა მხოლოდ ერთი მიმართულებით არ მიდის.

აქამდე ბუნებრივი სურათი იყო:

~~~text
REAL
→ contact / projection
→ concepts
→ field
→ ideal construction
~~~

მაგრამ შიდა კონსტრუქციულ სამყაროს შეუძლია თვითონ წარმოქმნას ისეთი მოთხოვნა,
რომლის შესაბამისი რეალურ სამყაროში ჯერ არც ნაპოვნია და შეიძლება საერთოდ არც იყოს
შექმნილი.

ამიტომ მეორე, თანაბრად მნიშვნელოვანი მოძრაობაა:

~~~text
IDEAL
→ construction
→ structural need
→ abstract requirements concept
→ search / query / measure / trap / design
→ REAL
~~~

ეს მეორე მოძრაობა არ არის პირველი გზის უბრალო „უკან დაბრუნება“.

> **ზვავის საწყისი შეიძლება პირდაპირ იდეალურ სამყაროში გაჩნდეს.**

## 1. რატომ არის შიდა სამყარო „იდეალური“

„იდეალური“ აქ არ ნიშნავს სრულყოფილს ან რეალობისგან დამოუკიდებელ ფანტაზიას.

იგი ნიშნავს, რომ შიდა კონსტრუქცია შეიძლება დაეყრდნოს ისეთ **განყენებულ,
ფუნდამენტალურ ცნებებსა და კანონებს**, რომლებიც რეალურ სამყაროში ყოველთვის
შერეული, ხმაურიანი და კონკრეტული მატარებლებით გვხვდება.

მაგალითად შიგნით შეიძლება იმუშაოს:

~~~text
ადგილი
რიგი
ზომა
ნაწილი / მთელი
იგივეობა
მიზეზობრივი მიმართულება
შესაძლებლობა
უარყოფა
~~~

და ამ სუფთა კავშირებით ააგოს სტრუქტურა მანამდე, სანამ კონკრეტული გარე მატარებელი
დადგინდება.

ამიტომ შიდა სამყარო არა მხოლოდ მიღებული რეალობის შეკუმშული ასლია.

> **მას შეუძლია ისეთი სტრუქტურის აგება, რომლის გარე რეფერენტი ჯერ საძებნია ან ასაგებია.**

## 2. მოთხოვნის ცნება

**აბსტრაქტული მოთხოვნების ცნება** არის შიდა კონსტრუქციის მიერ დაბადებული
მისამართიანი ცნება, რომელსაც ჯერ არ აქვს დადგენილი გარე რეფერენტი, მაგრამ
კონსტრუქციამ უკვე შეუქმნა **მოთხოვნების ბლოკი**: რა თვისებები, კავშირები,
საზღვრები ან როლები უნდა ჰქონდეს შესაძლო შესაბამისს.

შემდგომ ტექსტში მოკლედ ვუწოდებთ **მოთხოვნის ცნებას**.

მარტივი სახე:

~~~text
A ──requires──> X
X ──must_fit──> B
X ──before────> C
X ──has────────> P
~~~

აქ `X` ცარიელი ადგილი აღარ არის.

იგი უკვე **სტრუქტურულად დატვირთული ცნებაა**.

შეიძლება ჯერ არ ვიცოდეთ:
- რა ჰქვია;
- სად არის;
- არსებობს თუ არა;
- ერთია თუ რამდენიმე;
- უნდა ვიპოვოთ თუ უნდა ავაგოთ.

მაგრამ უკვე ვიცით, **რა ურთიერთობებში უნდა ჩაჯდეს**.

### არქეოლოგიური ჭურჭლის მაგალითი

ძველი თიხის ჭურჭლის ფრაგმენტების აღდგენისას დაკარგული ნაწილი ჯერ ხელში არ გვაქვს,
მაგრამ არსებული ნატეხების ფორმა უკვე განსაზღვრავს, **როგორი უნდა იყოს დაკარგული
შუა ნაწილი**, რომ მთლიანობა შეიკრას.

აღდგენისას არქეოლოგი ამ ადგილს შეიძლება სხვა მასალით ავსებდეს. ეს შევსება არ ნიშნავს,
რომ სწორედ ასეთი ნატეხი იქნა ისტორიულად ნაპოვნი. ის ინახავს **დაკარგული ნაწილის
კონსტრუქციულ ფორმასა და მოთხოვნებს**.

Noepedia-ში აბსტრაქტული მოთხოვნების ცნება ზუსტად ამ როლს თამაშობს:

~~~text
არსებული სტრუქტურა
→ აკლებული ადგილი
→ მოთხოვნების ფორმა
→ მოთხოვნის ცნება
→ ძიება / შესაბამისობა / აგება
~~~

ამიტომ ერთმანეთისგან უნდა დარჩეს გარჩევადი:

~~~text
რას ითხოვდა სტრუქტურა
≠
რა ვიპოვეთ ან ავაგეთ ამ ადგილის შესავსებად
~~~

## 3. OPEN და აბსტრაქტული მოთხოვნების ცნება ერთი რამ არ არის

### OPEN

ამბობს:

> აქ რაღაც დაუხურავია.

### მოთხოვნის ცნება

ამბობს:

> ჯერ არ ვიცი რა ხარ, მაგრამ უკვე ვიცი იმდენი შენს შესახებ,
> რომ შეიძლება შენი ძებნა, განსხვავება ან აგება დავიწყო.

ამიტომ მოთხოვნის ცნება არის **ფორმირებული უცნობი**.

OPEN შეიძლება საერთოდ უშინაარსო იყოს:

~~~text
A → ? → B
~~~

მოთხოვნის ცნება კი უკვე მოთხოვნების ბლოკს ატარებს:

~~~text
მოთხოვნების_ცნება_X
├─ REQUIREMENT: location ∈ REGION_R
├─ REQUIREMENT: supports LOAD_L
├─ REQUIREMENT: precedes EVENT_C
└─ REQUIREMENT: compatible_with RULE_Q
~~~

ამ ეტაპზე ჯობს სწორედ **მოთხოვნები** შევინახოთ და არა წინასწარ დაწერილი მოქმედების
პირობები. რა ოპერაცია მოჰყვება ამ მოთხოვნებს — ძიება, კითხვა, გაზომვა, trap თუ
დიზაინი — კონკრეტული კონსტრუქციის გაგრძელებამ უნდა გადაწყვიტოს.

## 4. შიდა თანმიმდევრულობის კარიბჭე

მოთხოვნის ცნება გარეთ გასვლამდე ჯერ შიგნით უნდა შემოწმდეს.

~~~text
მოთხოვნის ცნება
→ INTERNAL CONSISTENCY CHECK
   ├─ INCOHERENT → CONFLICT / REOPEN
   └─ CONSISTENT → outward operation allowed
~~~

თუ მოთხოვნების ბლოკი საკუთარ თავთან წინააღმდეგობაშია, SEARCH, QUERY, MEASURE,
TRAP ან DESIGN არ უნდა გაეშვას. ჯერ თვითონ შიდა კონსტრუქციაა გასასწორებელი.

## 5. მოთხოვნის ცნების კანდიდატთა სივრცე

მოთხოვნის ცნების გარე შესაბამისი თავიდან შეიძლება მრავალი იყოს.

~~~text
Cand(მოთხოვნების_ცნება_X) = {a, b, c, d, ...}
~~~

ყოველი ახალი შიდა ან გარე შეზღუდვა ამ სივრცეს ცვლის:

~~~text
constraint₁
→ {a, b, c, d}

constraint₂
→ {a, c, d}

constraint₃
→ {c}
~~~

აქ მთავარი არაა წინასწარ ალბათობის მიწერა.

მთავარია, რომ სისტემა პატიოსნად ინახავდეს:
- რომელი კანდიდატებია ჯერ დასაშვები;
- რის გამო გამოირიცხა თითოეული;
- რომელი შეზღუდვაა შიდა;
- რომელი მოვიდა გარე კონტაქტიდან;
- რომელი ჯერ მხოლოდ ჰიპოთეზაა.

## 6. binding — როცა შესაბამისი მოიძებნა

თუ საბოლოოდ ერთი ან რამდენიმე გარე ობიექტი აკმაყოფილებს მოთხოვნის ცნების მოთხოვნებს,
მოთხოვნის ცნება **არ ქრება**.

ამის ნაცვლად იწერება კავშირი:

~~~text
მოთხოვნების_ცნება_X ──realized_by / bound_to──> REAL_OBJECT_731
~~~

ეს მნიშვნელოვანია, რადგან უნდა დარჩეს განსხვავება:

~~~text
რას ვეძებდით
≠
რა ვიპოვეთ
~~~

თუ ნაპოვნი ობიექტი მხოლოდ ნაწილობრივ შეესაბამება მოთხოვნას, ეს განსხვავებაც
მისამართიანი რჩება.

მოთხოვნის ცნების შენარჩუნება გვაძლევს:
- ძიების provenance-ს;
- დიზაინის მოთხოვნის ისტორიას;
- ალტერნატიული რეალიზაციების შედარებას;
- იმ პირობების ცოდნას, რომლებშიც binding უნდა REOPEN-დეს.

## 7. ორი გარე გზა — აღმოჩენა და გამოგონება

მოთხოვნის ცნების გარეთ გასვლა ორ ძირითად რეჟიმად იყოფა.

### 7.1 SEARCH — „იპოვე ის, რაც უკვე არსებობს“

~~~text
მოთხოვნის ცნება
→ candidate search
→ observation / retrieval / measurement
→ compare with constraints
→ BIND or remain OPEN
~~~

ეს არის აღმოჩენის რეჟიმი.

### 7.2 DESIGN — „თუ არ არსებობს, ააგე“

~~~text
მოთხოვნის ცნება
→ no adequate external match
→ treat constraints as design target
→ construct candidate
→ test
→ realized_by
~~~

ეს არის ინჟინერული რეჟიმი.

ერთსა და იმავე მოთხოვნის ცნებას შეუძლია ჯერ SEARCH სცადოს და მერე DESIGN-ზე გადავიდეს.

მაგალითად:

~~~text
მჭირდება რაღაც, რაც:
- ამ სივრცეში ჩაეტევა
- ამ დატვირთვას დაიჭერს
- ამ მიმართულებით იმოძრავებს
- ამ შეზღუდვას არ დაარღვევს
~~~

სისტემა ჯერ შეიძლება ეძებდეს მზა დეტალს.

მაგრამ **„ვერ ვიპოვე“ ≠ „არ არსებობს“**. თუ ძიების არე `open` იყო,
SEARCH-ის მარცხი ნიშნავს `SEARCH_OPEN`-ს და არა ავტომატურ გადასვლას DESIGN-ზე.
DESIGN_TARGET გამართლებულია მხოლოდ მაშინ, როცა ძიების შესაბამისი არე საკმარისად
დახურული იყო, ან ამოცანა თავიდანვე ითხოვს ახალი რეალიზაციის აგებას.

## 8. active learning — რას ვკითხოთ გარეთ

თუ მოთხოვნის ცნების რამდენიმე კანდიდატი დარჩა, შემდეგი კონტაქტი შემთხვევითი არ უნდა იყოს.

სისტემა უნდა ეძებდეს:

> **რომელი დაკვირვება ან კითხვა ყველაზე მეტად შეამცირებს დარჩენილ თავისუფლებას?**

მაგალითად:

~~~text
Cand(X) = {A, B, C, D}

query Q:
A,B → YES
C,D → NO
~~~

ასეთი კითხვა კანდიდატთა სივრცეს ძლიერად ყოფს.

ამით მიიღება ციკლი:

~~~text
IDEAL:
რომელი მოთხოვნის ცნება არის დასაზუსტებელი?
        ↓
რომელი თვისება ყველაზე მეტად განასხვავებს კანდიდატებს?
        ↓
OUTWARD QUERY / MEASURE / SEARCH
        ↓
REAL CONTACT
        ↓
ახალი constraint
        ↓
IDEAL UPDATE
~~~

ეს არის active learning-ის არქიტექტურული ადგილი Noepedia-ში.

## 9. კავშირი D2-სთან — ყველაზე ცოტა უცნობი

შიდა სივრცეში D2 ეძებს ყველაზე შეზღუდულ ხვრელს:

~~~text
x* = argmin Freedom(x)
~~~

IDEAL_TO_REAL მოძრაობაში ამას ემატება მეორე კითხვა:

~~~text
არჩეულ მოთხოვნის ცნებაზე:
რომელი გარე მოქმედება მაქსიმალურად შეამცირებს Freedom-ს?
~~~

ამიტომ ერთი სრული ნაბიჯი შეიძლება იყოს:

~~~text
1. აირჩიე ყველაზე შეზღუდული OPEN / მოთხოვნის ცნება
2. გამოთვალე, რა გვაკლია binding-მდე
3. აირჩიე ყველაზე ინფორმაციული გარე კონტაქტი
4. მიიღე ახალი ფაქტი
5. განაახლე constraints
6. თავიდან გაავრცელე
~~~

## 10. Kairos — როცა საჭირო გაზომვა ახლა შეუძლებელია

ზოგი საჭირო დაკვირვება ახლავე ვერ კეთდება.

მაგალითად:

> როცა ობიექტი `STATE_Q`-ში შევა, გაზომე `P`.

მაშინ მოთხოვნის ცნების აქტიური სწავლა შეიძლება გადაიქცეს ხაფანგად:

~~~text
მოთხოვნის ცნება მოითხოვს თვისებას P
→ required situation S
→ TRAP(S)
→ wait
→ KAIROS
→ INTERRUPT
→ MEASURE(P)
→ განაახლე მოთხოვნის ცნება
~~~

ამიტომ trap/Kairos სისტემა მხოლოდ შეხსენების მექანიზმი არაა.

იგი შეიძლება იყოს **იდეალური სამყაროდან წამოსული კვლევითი მოთხოვნის
გარე მომავალში გაჩერებული გაგრძელება**.

## 11. ორი ზვავი

მიმდინარე არქიტექტურაში სასარგებლოა ორი ზვავის გარჩევა.

~~~text
REAL
~~~


შემდეგ გარე პასუხი ისევ შემომავალ ზვავად ბრუნდება.

## 12. მოთხოვნის ცნების სამუშაო lifecycle

პირველი სამუშაო სტატუსები:

~~~text
ABSTRACT
  ↓
CONSISTENCY_CHECK
  ├─→ INCOHERENT → CONFLICT / REOPEN
  └─→ CONSISTENT
          ↓
       SEARCHING
  ├─→ BOUND
  ├─→ PARTIAL_BIND
  └─→ DESIGN_TARGET
          ↓
       PROTOTYPE
          ↓
       TESTED_BIND
~~~

მნიშვნელობები:

- **ABSTRACT** — მხოლოდ შიდა მოთხოვნებით არსებობს;
- **CONSISTENCY_CHECK** — ამოწმებს, თავსებადია თუ არა მოთხოვნების ბლოკი საკუთარ თავთან;
- **INCOHERENT** — მოთხოვნები ერთმანეთს ეწინააღმდეგება; გარეთ გასვლა აკრძალულია;
- **CONSISTENT** — შიდა კარიბჭე გავლილია და გარე ოპერაცია დასაშვებია;
- **SEARCHING** — გარე შესაბამისებს ეძებს;
- **BOUND** — გარე შესაბამისი დადგენილია საჭირო scope-ში;
- **PARTIAL_BIND** — შესაბამისობა ნაწილობრივია;
- **DESIGN_TARGET** — არსებული შესაბამისი ვერ მოიძებნა ან განზრახ ასაგებია;
- **PROTOTYPE** — დიზაინიდან რეალურ კანდიდატად გამოვიდა;
- **TESTED_BIND** — bridge/certificate-ის ფარგლებში დამოწმებულია.

ეს ჯერ მონაცემთა საბოლოო სქემა არაა.

პირველი უფრო ხშირად რეალურიდან იდეალურისკენ მოდის.
