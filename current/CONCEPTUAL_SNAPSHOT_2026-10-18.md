# CONCEPTUAL SNAPSHOT — სხვენიდან ხედი

**Status: HISTORICAL META-SNAPSHOT / CURRENT ORIENTATION**  
**Date: 2026-10-18**

ეს ფაილი არ არის ახალი კანონი, ახალი core-spec ან ძველი დოკუმენტების გადაწერა.

ეს არის დროითი ნიშანი: **სად მოვედით, რას ვხედავთ ახლა და საით გვიჩვენებს გზა.**
მისი დანიშნულებაა მომავალში შეგვეძლოს ზუსტად დავინახოთ არა მხოლოდ საბოლოო
არქიტექტურა, არამედ აზრის მოძრაობაც — რას ვაკეთებდით, რა შეგვამჩნევინა ამ გზამ,
რა შეიცვალა ჩვენს კითხვაში და რას ველოდებით შემდეგ.

## უკან გახედვა — საიდან მოვედით

Noepedia თავიდან ადვილად შეიძლებოდა გაგვეგო როგორც ცოდნის საცავი, ქსელი ან
ინფრასტრუქტურა, სადაც სამყაროზე მიღებული ინფორმაცია ინახება და შემდეგ იკითხება.

მაგრამ ექსპერიმენტებმა და კონსტრუქციულმა ზონდებმა თანდათან სხვა რამ გამოაჩინა.

მთავარი სირთულე არ აღმოჩნდა თვით ობიექტების არსებობა. სირთულე იწყება იქ, სადაც
უნდა გადავწყვიტოთ:

- რომელი ობიექტი რომელთან რა კავშირშია;
- როდის არის ორი ჩანაწერი ერთი და იგივე ობიექტის შესახებ;
- რომელი დასკვნა გამომდინარეობს მოცემული წესებიდან და რომელი მხოლოდ მოსახერხებელი
  ინტერპრეტაციაა;
- რა არის მიმდინარე, რა — ისტორიული;
- რომელი წესი მოქმედებს ამ scope/time-ში;
- სად გვაქვს რეალური წინააღმდეგობა და სად უბრალოდ აკლია სტრუქტურა ან ინფორმაცია.

ამან შეცვალა დემონის როლიც.

დემონი აღარ განიხილება როგორც „ჭკვიანი აგენტი“, რომელსაც დარგობრივი ცოდნა უნდა
ჰქონდეს. პირიქით, მისი სასურველი მდგომარეობაა **შინაარსობრივი სიღარიბე და
სტრუქტურული სიზუსტე**.

იგი უფრო ჰგავს პორტის მმართველს, საწყობის ოპერატორს ან ინფრასტრუქტურულ ლოგისტიკოსს:
არ წყვეტს რა არის სამყაროში ჭეშმარიტი თავისი common sense-ით, მაგრამ ზუსტად იცის
მისამართები, კავშირები, წესები, provenance, scope, time, current/history და
რომელი ცვლილება რა პროცედურით შეიძლება შევიდეს ქსელში.

ამ გზაზე განსაკუთრებით მნიშვნელოვანი გახდა STOP/NEED განსხვავება.

სისტემა არ უნდა შეფასდეს მხოლოდ იმით, რამდენ პასუხს იძლევა. მისი ხარისხის
ცენტრალური ნაწილი არის ისიც, **რამდენად სწორ ადგილას შეუძლია გაჩერება**.

თუ აკლია გარე ფაქტი — უნდა შეძლოს ASK.
თუ მოქმედი წესი კრძალავს გზას — BLOCK.
თუ თვით ქსელს აკლია ისეთი სტრუქტურა, რომლის გარეშეც სწორი კითხვაც ვერ ყალიბდება —
NEED.

ამიტომ გაჭედვა შეცდომა აღარ არის.

> **გაჭედვა არ არის სისტემის მარცხი; გაუგებარი გაჭედვაა მარცხი.**

## რა შევამჩნიეთ გზაში

ყველაზე მნიშვნელოვანი აღმოჩენა ის იყო, რომ Noepedia-ს ზრდა შეიძლება თვით
გაჭედვებიდან მივიღოთ.

დემონი მიდის იქამდე, სადამდეც კანონიერად შეუძლია. იქ, სადაც ვეღარ მიდის, ჩვენ არ
ვაწვდით კონკრეტულ პასუხს. ვკითხულობთ: **რომელი ყველაზე პატარა ზოგადი სტრუქტურა
აკლდა?**

თუ იგივე ნაკლებობა დამოუკიდებელ სცენებში მეორდება, იგი უკვე აღარ ჰგავს ერთჯერად
patch-ს. იგი ხდება ახალი სამუშაო relation-ის, policy-ის, qualifier-ის ან executor
capability-ის კანდიდატი.

ამიტომ სისტემა წინასწარ დასრულებულ ontology-ს აღარ ითხოვს.

მისი ზრდის ფორმა ასეთია:

~~~text
მოქმედი ქსელი
→ lawful construction
→ STOP / NEED / CONFLICT / OPEN
→ განმეორებადი სტრუქტურული ხვრელი
→ მინიმალური ახალი მექანიზმი
→ იგივე სცენის ხელახალი გავლა
~~~

ამ გზაზე provenance ცენტრალური ობიექტი გახდა.

ერთი და იგივე შედეგს შეიძლება რამდენიმე დამოუკიდებელი გზა ჰქონდეს.
**same result ≠ same provenance.**

ამის გამო „რა ვიცი?“ და „რის საფუძველზე ვიცი?“ ერთმანეთისგან აღარ იყოფა.
საყრდენები, მათი composition, მათი ცვლილება და downstream შედეგები თვითონაც
მისამართიანი სტრუქტურის ნაწილი ხდება.

ასევე გაიყო ისტორიული ფაქტი და მიმდინარე epistemic სტატუსი.

Committed წარსული არ იშლება, მაგრამ მისი მიმდინარე მოქმედება შეიძლება შეიცვალოს.
ამიტომ correction არ ნიშნავს history rewrite-ს.

> **past commit fact is preserved; present trust/status is revisable.**

შემდეგ თვით წესებიც იმავე სამყაროში მოხვდა: მათაც აქვთ applicability, scope, time,
policy, conflict და provenance. აქედან მივედით finite justification graphs,
termination/confluence განსხვავებამდე და edge-local dependency propagation-მდე.

## აწმყო — რას ვაშენებთ სინამდვილეში

დღევანდელი ხედვით Noepedia არ არის უბრალოდ ცოდნის საცავი.

იგი არის ინფრასტრუქტურა, სადაც:

~~~text
რეალური კონტაქტი
→ addressable observations / concepts / relations
→ provenance-preserving field
→ constructive world
→ lawful build
→ PASS / OPEN / ASK / NEED / BLOCK
→ ახალი კონტაქტი ან ახალი სტრუქტურული მოთხოვნა
~~~

დემონის მთავარი ამოცანა არის არა სამყაროს მნიშვნელობის გაგება, არამედ ამ მოძრაობის
კანონიერი ლოგისტიკა.

მისი ბირთვის სასურველი თვისებაა:

> **რაც შეიძლება ნაკლები domain semantics, მაგრამ იმდენი structural discipline,
> რომ ქსელი არ დაიჯღაპნოს.**

დღეს ყველაზე მკაფიო executor საზღვარია transaction membrane:

~~~text
PROPOSE → CHECK → COMMIT
~~~

და ახალი delta ვერ იყენებს თავისივე ახლად შემოტანილ წესს საკუთარი ავტორიზაციისთვის.

ეს არის პატარა, მაგრამ ფუნდამენტური მემბრანა: ქსელს შეუძლია შეიცვალოს, მაგრამ არ
შეუძლია იმავე მოქმედებით საკუთარი შემოწმების კარი გააუქმოს.

GW01-მა ამ არქიტექტურის საინტერესო საზღვარი გვაჩვენა: honesty დიდწილად მუშაობდა,
მაგრამ ძალა აკლდა რამდენიმე ადგილზე.

ამიტომ ახლა გვაქვს ოთხი WORKING candidate:

- გარე წყარო პირდაპირ არ წერს ქსელში; იგი მხოლოდ PROPOSE-ს აკეთებს provenance/time-ით;
- explicit TASK-ს შეუძლია scoped მოთხოვნის ცნების დაბადების ავტორიზაცია;
- trap/watch-ის შინაარსი ქსელშია, ხოლო post-COMMIT affected-watch reevaluation
  executor-ის საქმეა;
- თუ predicate-ის multiplicity/cardinality უცნობია და რამდენიმე CURRENT target ჩანს,
  სისტემა ამას visible OPEN-ად წერს და არც single-valued, არც multi-valued semantics-ს
  არ იგონებს.

ეს ოთხი ჯერ არ არის გაყინული invariant. ისინი უნდა გაიარონ fresh, დამოუკიდებელი
გადამოწმება.

## წინ გახედვა — რა ჩანს ახლა

ახლა ყველაზე სასარგებლო შემდეგი ნაბიჯი აღარ არის კიდევ ბევრი ახალი მეტა-წესის
წინასწარ მოფიქრება.

პირველი ხილული გზა არის **ჰოლოგრამისგან მექანიზმის გამოყოფა**.

აქამდე დემონის როლს ხშირად LLM ასრულებდა. ამიტომ ყოველთვის რჩებოდა ეჭვი:
რომელი შედეგი მოდიოდა სპეციდან და რომელი — შემსრულებლის common sense-იდან?

GW02 სწორედ ამ საზღვარს ზომავს.

იგივე წესები უნდა გაეშვას დეტერმინისტულ, გონების გარეშე executor-ზე.
ყველა განსხვავება უნდა დაიყოს:

~~~text
SPEC_HOLE
LLM_ERROR
SEMANTIC_BY_NATURE
~~~

ეს გვაძლევს არა მხოლოდ ტესტს, არამედ შესაძლო აღმოჩენას: **ზუსტად სად მთავრდება
მექანიკური დემონი და სად იწყება ჰოლოგრამის/LLM-ის რეალური საჭიროება.**

შემდეგი მიმართულებები, რომლებიც ამავე ხედიდან ჩანს:

- fresh sealed rerun-ით GW01-ის ოთხი candidate-ის გადამოწმება;
- deterministic demon-ის საზღვრის გაზომვა;
- ASK-ის რეალური ინტერფეისის ჩამოყალიბება იქ, სადაც მექანიკა კანონიერად ვერ წყვეტს;
- მოთხოვნის ცნების სრული lifecycle-ის შემოწმება რეალურ კონტაქტამდე;
- watch/Kairos-ის ისე გამართვა, რომ trigger მექანიკურია, ხოლო semantics ქსელში რჩება;
- OPEN-ების გამოყენება არა როგორც „უცოდინარობის ნაგვის ყუთი“, არამედ როგორც
  მისამართიანი სამუშაო სტრუქტურა;
- ბოლოს — დაბრუნება უფრო მდიდარ Glass World-ებზე და შემდეგ რეალურ bridge-ებზე,
  სადაც უკვე ზუსტად ვიცით რომელ ნაწილს რას ვთხოვთ.

## სხვენიდან ერთი სურათი

დღეს Noepedia ასე ჩანს:

~~~text
სამყარო რაღაცას გვაწვდის
        ↓
ქსელი მისამართიან კავშირებად ინახავს
        ↓
კონსტრუქცია ამოწმებს, რა შეიძლება აშენდეს
        ↓
დემონი არ იგონებს — მოძრაობს, ამოწმებს და ჩერდება
        ↓
გაჩერება ხილულ OPEN / NEED / ASK / BLOCK-ად იქცევა
        ↓
განმეორებადი ხვრელი გვიჩვენებს ახალ საჭირო სტრუქტურას
        ↓
ქსელი იზრდება არა პასუხების დაგროვებით,
~~~
